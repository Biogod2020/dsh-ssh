# 真实 SSH 历史与恢复测量

[完整 CI](https://github.com/Biogod2020/dsh-ssh/actions/runs/39841108871) 已通过，源码提交 `43016e2f92bb2c1dae54fca7f4e070b134652fce`。Ubuntu 24.04 x64 runner、Node 24.16.0、DSH 0.2.1-rc.2；生成的 SSH 身份、严格 known_hosts、独立 Home，没有用户历史或模型请求。

同一候选控制器分别使用冻结 jay.39 缓存实现与分段缓存。这里只比较存储实现，不是新旧完整插件的端到端对比。夹具含 1,104 个事件（约 3.64 MB，其中一个约 3 MiB 的非重复大事件）；本机末窗、无变化同步各 100 次，逐条新增、断线恢复各 30 次。每格为 p50 / p95，单位 ms。

| 注入 RTT / 每方向带宽 | 缓存 | 本机末窗 | 无变化同步 | 单条新增落盘 | SSH + 服务恢复 |

| 200 ms / 2 Mbit/s | 分段候选 | 0.67 / 0.97 | 746.31 / 1414.10 | 750.77 / 1417.26 | 2730.05 / 2774.54 |

三组候选均为：无变化时 0 条历史正文、0 字节历史写入、0 次旧段重写；新增 30 条共返回 30 个记录（15,600 字节正文），应用写入合计 45,384 字节，旧段重写为 0。冻结 v1 同样已做到无变化零正文，但新增共重写 109,505,565 字节，旧会话数据文件发生重写。本机末窗每次应用读取从 3,641,599 字节降到 54,259 字节。

网络正文与总流量分开记账。例如 80 ms 候选的 100 次无变化检查仍发送 524,908、接收 74,288 字节的 SSH TCP 载荷，包含读取脚本、加密和保活等开销。此次存储改动没有消除这些开销，也没有证明网络恢复比旧缓存更快。30 次候选恢复 p95 为 1.19 秒，低于既定正常网络后台五秒门槛；这不替代原生界面可交互验收。

每一组均无失败，并验证原远端 DSH PID 保留。首次复制每组仅一次，80 ms 候选观测为 2.95 秒、200 ms / 2 Mbit/s 为 15.66 秒；单次数据只作诊断，不计算正式冷路径 p95。

测量边界：

- 用户态代理按每方向半 RTT、带宽和背压传递有序字节；四项校准测试验证二进制顺序、半关闭和断线。未注入内核丢包，报告明确为 0%；不以丢弃 TCP 字节冒充丢包。
- 总流量计 SSH 加密后的 TCP 载荷，未计 IP/TCP 首部与重传；本机 IO 为应用异步读写字节，未计物理 SSD 写入。
- 恢复到认证网关健康且工作区快照可读为止；不含原生渲染、模型输出和公网路由抖动。
- 两种缓存按固定顺序运行，未清除操作系统文件缓存；保活和 runner 负载造成的差异完整保留，不作为统计显著性或整体速度优势。

复现：先用 `scripts/fetch-history-baseline.mjs` 取回固定基线（对象哈希校验），再按 CI 的 `network-history` 步骤运行 `scripts/network-history-benchmark.mjs`。六份原始 JSON 保留全部 p50/p95/max、IO、流量和失败记录；`sha256.json` 校验与 CI 下载原件一致。1% 内核丢包、3/30/300 秒离线与原生点击/首屏/暖切换仍单独验收。
